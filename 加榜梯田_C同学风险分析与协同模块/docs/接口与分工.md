# A / C / B 对接说明

本文件使用你们图片中的分工：A为图像分析，B为地形与路径，C为气象风险。参考仓库内部的字母编号不同。核对的是提交`1a6d26b417ee15d1980b7e1a14e1c292dd527693`，不是保证今后所有版本均兼容。

## 1. A 已有内容与需要补充的内容

已核对`api/main.py`：`POST /analysis/full`是`/analyze`别名，上传表单键为`file`，成功外层为`success/status/message/data/timestamp`。完整结果中的异常值在`data.anomaly`；`/anomaly`或`/anomaly/detect`则直接放在`data`。

| A当前字段 | C怎样使用 |
|---|---|
| `low_vigor_fraction` | 低绿度候选像素数/全部图像像素数；0到1，不是病害比例 |
| `bare_land_fraction` | 保留为图像背景，裸地可能是正常田埂或休耕地，不自动当灾害 |
| `vegetation_fraction_gli` / `_vari` | 植被近似覆盖率，不能叫NDVI |
| `index_statistics` | 检查有限值和当前代码约定范围；不把旧版本异常数值悄悄截断 |
| `low_vigor_mask` / `bare_land_mask` | 相对服务URL，仅保留，不当作GeoJSON |
| `segmentation.class_distribution` | 七类比例；可描述场景，不等于经过核准的田块边界 |
| `timestamp` | 分析处理时间；绝不自动当拍摄日期 |

适配器要求附带一个`metadata`对象：

```json
{
  "observation_id": "真实观测的唯一编号",
  "plot_id": "与B一致的真实田块编号",
  "site_id": "jiabang_initial_aoi",
  "captured_at": "2025-06-24T10:00:00+08:00",
  "image_scope": "single_plot_crop",
  "location_verified": true,
  "plot_association_verified": true,
  "source_reference": "拍摄记录、裁剪过程及关联依据的文件或记录编号",
  "is_synthetic": false
}
```

上面的日期仅展示格式，不能给没有拍摄记录的图像套用该日期。`true`表示已经由团队核准，不是让你直接照填。影像最好先按真实田块裁剪再交A分析；当前模块不对整景比例做猜测式田块分摊，也不直接做像素到地理坐标转换。

若未来要定位具体异常斑块，需要A/B提供经过核准的CRS、仿射变换、影像裁剪范围和田块交叠信息，再将异常掩膜矢量化。当前输出只支持已核准田块整体的巡检需求。

### 对参考仓库的三点具体核验

1. `analysis/anomaly.py`计算`low_vigor.mean()`，分母是整图，不是植被像素数。适配器保留这一含义。
2. `api/main.py::run_predict`存盘前对训练编码加1，输出灰度值1-7；`run_segmentation`的`pred_mask`却指向彩色掩膜。文档中的“输出0-6”不能直接用于所有存盘文件。
3. `datasets/preprocessing.py::compute_vari`当前裁剪到[-1,1]，但旧`outputs/analysis/summary.json`的3条结果均超范围。它们来自仓库LoveDA流程、没有加榜定位及拍摄日期，不能直接和2021-2025天气关联。请A用当前代码重新生成自己的真实数据结果；本包没有修改其仓库。

## 2. B 的建议输入约定

这是供团队确认的新接口，不声称B现有程序已经实现。输入为标准GeoJSON `FeatureCollection`，每个真实田块为`Polygon`或`MultiPolygon`，二维经纬度，必须在当前实验框内。

必需属性：

| 属性 | 含义 |
|---|---|
| `plot_id` | 与A关联元数据一致，不能重复 |
| `site_id` | `jiabang_initial_aoi` |
| `crs` | 统一到`EPSG:4326` |
| `crs_verified` / `boundary_verified` | 坐标与真实田块边界已经核准 |
| `boundary_source` | 边界来源和核准记录 |
| `is_synthetic` | 明确是否虚构；正式融合拒绝虚构输入 |

可选`drainage_problem`和`irrigation_problem`对象包含`present`、`verified`、带时区的`observed_at`和`source_reference`。本版只使用审查日期之前、30天内的核准记录；30天是原型证据时效约定，可在`integration.py`调整并记录版本，不是灌排设施故障的物理持续期。

坡度、相对高程、沟渠连通和障碍物可以保留在B自己的数据中。本版没有把“坡度大”自动翻译成“内涝高风险”，也不依靠粗DEM猜测田埂是否损坏。

## 3. C 的融合请求与输出

请求结构如下，完整可运行示例见`examples/fusion_synthetic_request.json`：

```json
{
  "as_of_date": "2025-06-24",
  "demo_mode": false,
  "plots": {"type": "FeatureCollection", "features": []},
  "a_observations": [{"metadata": {}, "response": {}}]
}
```

`as_of_date`表示北京时间该日期结束后的**历史回顾**，不是当天早晨的决策。只接受不晚于该日期、相隔不超过3个日历日的图像，并使用同田块最新一条已接受图像。日界线未统一及数据实际可获取时刻仍有限制，不能将此称为实时因果预测。

`inspection_requests`中每条包含：

- `plot_id`、`geometry`、`geometry_crs`：B提供的核准田块；没有虚构的目标点。
- `weather_event_types`、`observation_id`、`reasons`：可核对的天气及本地线索。
- `priority`：P1为二级天气信号配合相关本地线索；P2为其他已满足本地证据的候选。没有低绿度/相关灌排证据，不单凭统一天气给所有田块硬分级。
- `task_type=inspection_only`：只提核查需求；`flight_ready=false`。
- `chemical_or_fertilizer_dose=null`：没有农艺依据，不给施药施肥量。
- `execution_status=awaiting_B_route_and_site_checks`：等待B计算路线和现场约束。
- `unknowns`：保留作物生育期、异常原因和农艺核验等未知项。

无真实田块或定位证据时，`regional_candidates`仍有天气结果，`inspection_requests`保持空。图像错误写入`quarantined_observations`；对影像低绿度的解释保持“原因未知”。

## 4. C 服务端点

默认`http://127.0.0.1:8001`，统一成功/失败外层与A相近；业务错误在HTTP错误体`detail`内。

| 方法与路径 | 作用 |
|---|---|
| `GET /health` | 历史覆盖期与结果可用状态 |
| `GET /weather/daily?start=2025-01-01&end=2025-12-31` | 清洗后的日数据，最多1826条 |
| `GET /risk/daily?date=2025-06-24` | 指定日期的五类信号、指标和阈值 |
| `GET /risk/events?start=2024-01-01&end=2025-12-31` | 与请求时间段相交的连续候选过程 |
| `GET /risk/summary` | 年度统计及数据限制 |
| `POST /integration/fuse` | A图像和B田块证据融合，输出巡检需求 |

可用Python请求已运行的C服务：

```python
import json, httpx
from pathlib import Path
request = json.loads(Path("examples/fusion_synthetic_request.json").read_text(encoding="utf8"))
response = httpx.post("http://127.0.0.1:8001/integration/fuse", json=request)
response.raise_for_status()
print(response.json()["data"]["inspection_requests"])
```

这只是示例调用，不会在安装或运行历史分析脚本时自动连接A/B服务，也没有向同学发送任何结果。

## 5. 平台和数据库

PostgreSQL保存天气、风险事件、图像结果摘要及任务；PostGIS保存真实田块多边形。大型影像、DEM、掩膜继续保存在文件系统/对象存储，数据库只放URI、时间和来源，不塞入每个像素。Navicat用于连接和管理数据库。

`postgres_schema.sql`为建表草案，未在真实数据库执行。PostGIS扩展通常需要数据库管理员权限。现有数据仍以本包CSV/JSON为交付依据；团队确定表名、已有字段和数据库后再做迁移与导入，不能宣称现在已经落库。
